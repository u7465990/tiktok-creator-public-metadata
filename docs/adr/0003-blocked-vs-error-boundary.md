# `blocked` 与 `error` 的分界：对方限制 vs 自身故障

两者都表现为"没拿到数据"，但语义相反：`blocked` 表示平台限制了我们（限流、验证码、地区封锁），账号可能完全正常，该做的是降速、换时间、或如实上报；`error` 表示我们自己的程序坏了（解析器崩溃、磁盘满、未归类的超时），账号与平台都没有问题，该做的是修代码。把两者合并会让重试策略与告警对象同时失效，而且这个区分会渗透到缓存与重试逻辑里，事后拆分的成本很高。

## Considered Options

- **五态严格区分（采纳）**：与题面枚举一致，且能驱动不同的后续动作。
- **合并为 `error`**：实现简单，但丧失"该重试"与"该修 bug"的判别能力。
- **用 HTTP 状态码代替 status**：403/429/404 无法表达"账号私密"，也无法表达解析失败。

## Consequences

- 状态映射必须集中在一处（一个把"观察到的信号 → Status"的函数），禁止各处 `if 403: ...` 散落。
- 未识别的异常默认落到 `error`，不允许默认落到 `ok`；宁可少一条成功，不可多一条假成功。
- DNS 失败、连接被重置、代理不可用等**运行环境问题一律归 `error`**，不是 `blocked`。调研已实测到本机对 `www.tiktok.com` 的 DNS 被污染，这类失败如果记成 `blocked`，会把"环境坏了"误判成"平台封了我们"，从而诱导出错误的应对（降速、换 IP）。
